# Client credential clear audit

Baseline: `02f98f89a19b6c079517c9aae07df7edd0e600e5`. All assertions in `Tests/Middleware/ClerkDeviceTokenResponseMiddlewareTests.swift` were read and its SHA-256 matched [the baseline inventory](legacy-tests.json). This audit retires exactly that file's three declarations. The subsequent [request construction](request-construction-test-audit.md) and [client-sync](client-sync-middleware-test-audit.md) audits complete retirement of those mixed networking suites.

The backend's [client deletion handler](https://github.com/clerk/clerk_go/blob/33e0f8279c9b4e3d90d6e4788c67237bc6378a56/api/fapi/v1/clients/http.go#L306) calls [UnsetClientHandshakeCookie](https://github.com/clerk/clerk_go/blob/33e0f8279c9b4e3d90d6e4788c67237bc6378a56/api/fapi/v1/cookies/helpers.go#L192), which sends `Authorization: Bearer ` for a native client. The trailing space accommodates intermediaries that strip empty header values. Header implementations may normalize this to `Bearer`.

The shared transport previously persisted this value as a credential. It now removes the credential within its serialized acceptance queue and advances the credential revision, so an older response cannot restore the deleted credential. Failed storage removal is reported; subsequent requests can retry. Queued request preparation waits for removal. Non-native transport behavior is unchanged.

The supported deletion path is the existing Expo JavaScript owner with `experimental.persistClient: false`: canonical `Clerk.signOut()` invokes `Client.destroy()`. That TypeScript resource resets its client ID and sessions, and the attached projection publishes empty session/user roots. No native client-state reducer or new standalone configuration option is introduced. Standalone sign-out retains the canonical default that removes sessions while persisting the client. A synthetic blank-header response on an unrelated operation does not promise the old middleware's arbitrary `clerk.client = nil` behavior.

Expo's `TokenCache` permits implementations with only `getToken` and `saveToken`. Credential deletion and instance changes previously called optional `clearToken`, leaving those caches untouched. Both paths now use `clearToken` when available and otherwise save an empty client credential. Other cache entries are preserved, and a failing provided `clearToken` is not silently ignored.

The attached deletion tests run the real JavaScript owner in the test VM; they do not claim a live Expo application or browser authentication journey.
