# Identity Persistence and Sync

The device token and `Client` form one authentication identity. The token names a server-side Client, so two apps or devices holding the same token share one Client and only need to agree on the newest snapshot of it. The server stays the authority: whenever state is in doubt, the SDK keeps a token and refreshes the Client.

## One Record

`ClerkIdentityStore` persists `{deviceToken, client, serverDate}` as a single Keychain item, along with a `revision` UUID that changes on every write and an identity `epoch` that changes on clear or token replacement. Because it is one item, a reader never sees a token paired with another identity's Client. A clear writes a credential-free tombstone instead of deleting the item.

The last `clearEpoch` is retained across subsequent sign-ins. Each app records that clear in its local Watch generation once, even if it missed the tombstone and only sees the later sign-in. This prevents an old paired-device snapshot from restoring the pre-clear session.

The record lives in the configured Keychain (`KeychainConfig.service` and `accessGroup`), with the Clerk instance fingerprint in its account name. Different instances do not overwrite each other. The `clerkIdentityV4` account prefix identifies the conditional-write record format. With an access group, every app and extension in the group reads and writes the same item. Two exceptions keep the identity app-local, with sharing off: an app that adopted shared-session sync and then turned it off, and an app that lacks the group entitlement. These local identities use a separate service containing the app identifier and a hash of the configured service. Merely omitting an access group would still allow reads and updates to match the shared record.

A `Client` that no longer decodes, for example one written by a newer SDK in another app, is dropped while the device token is kept, so the next refresh restores it instead of signing the user out.

`ClerkIdentityController` commits the record before updating memory. Every write must succeed; failed persistence does not expose a new Client in memory. Keychain writes use `SecItemAdd` for creation and `SecItemUpdate` conditioned on the expected revision in `kSecAttrGeneric` for replacement. Revision and encrypted payload change in the same operation. Conflicts never fall back to unconditional upserts. Conditional records use one storage backend and never copy a legacy fallback over it.

Keychain access is deliberately synchronous on the main actor, preserving #579's write-to-storage-before-memory ordering without asynchronous persistence queues or drains. Slow Keychain calls can delay the UI, so device validation should measure their latency. Moving I/O off the main actor is not a prerequisite for this design; consider it if measurements justify the additional coordination across suspension.

## Shared-Session Sync

Whenever the resolved identity backend is in an access group, the controller also:

1. Re-reads the record's revision before capturing a request identity, applying a response, applying a Watch transition, or replacing the device token, and on foreground. If another process wrote since this app last read or wrote, it adopts that identity.
2. Posts a Darwin notification after each write and when starting sync, covering migration and recovery performed before notifications were installed. Other apps re-read on receipt. Reading does not post, so notifications cannot loop.

This follows the actual storage selection, including a group writer that has not enabled `sharedSessionSync`. An app that disabled sharing after adoption, or uses missing-entitlement fallback, keeps its isolated local backend and does not reconcile with the group.

Adopting a different identity epoch fences in-flight responses (`clientResponseGeneration`). This detects a missed clear even when the same token has since been reused. Adopting a newer snapshot within the same epoch sets a server-date floor; same-second responses with an older Client `updatedAt`, and undated responses below that established floor, are rejected.

Explicit server clears have no Client `updatedAt`. They can tie that floor when their response sequence is current, while older sequences, older or missing server dates, and stale identity generations remain rejected.

A competing write makes the conditional update fail. The controller reloads the winner without rebasing a prepared response. A successful server mutation stays successful: when the identity epoch is unchanged, the SDK makes one fresh canonical Client read, then resolves the original auth-flow completion against the adopted session. Hosted-auth redemption also receives this recovery: it consumes a nonce through a physical POST, even though it returns a canonical Client. A conflicting canonical GET adopts the winner and stops. If the recovery read fails, the SDK retains the adopted state and logs the failure; normal refresh handles subsequent reconciliation. The mutation is never repeated for a storage conflict. Watch and explicit token transitions still report conflicts to their callers.

Explicit clears make one conditional attempt and report failure. Before reading shared storage, a clear persists a credential-free intent in app-local storage, scoped to the Clerk instance and target Keychain configuration. Once read, the intent also records the target identity epoch. Requests remain blocked after a failed clear. On restart, recovery clears that same epoch before hydration, but preserves a later identity epoch; a crash after committing the tombstone therefore cannot wipe a subsequent login. Successful cleanup removes the intent. There are no fixed-count retry loops.

`sharedSessionSync: .enabled` additionally requires an access group and a bundle identifier. On first use, it prepares app-local private state as described in [Private State](#private-state), preserving trusted app-local values without importing ambiguous shared credentials.

## Response Payloads

Network responses enter `ClerkIdentityController.applyNetworkResponse` once through response middleware. Hosted-auth redemption and session activation deliberately defer that same handler until their operation-specific checks or cleanup finish. `refreshClient()` returns the controller's accepted identity after the request; it never reapplies the decoded HTTP snapshot. This matters when a conditional write loses: the returned network payload may differ from the identity that won in storage.

Mocked refreshes supply synthetic HTTP responses to the same request and response middleware, with the owning API client's runtime and request sequence. Mock and preview identities use isolated in-memory storage with a matching device token and Client. Production persistence has no memory-only exception for incomplete fixtures. Tests opt into isolated configuration explicitly; running under a test process does not change normal configuration or migration behavior.

Frontend mutation responses can carry the operation result in `response` and the authoritative Client snapshot in sibling `client`. Error responses can carry the snapshot in `meta.client`. A removed Session plus a signed-out Client is a normal Client update, not an identity clear.

Null piggyback fields mean no Client update. A canonical `/v1/client` response with `response: null` and `client: null` is also preserve/no-update, including backend database-maintenance responses. Native client deletion is the explicit clear path: `DELETE /v1/client` clears the device token and identity when the response has `Authorization: Bearer `.

Request sequence, client-response generation, canonical-client flag, and request device token form one response checkpoint. Response metadata also retains the physical HTTP method to distinguish canonical reads from redemption.

## Watch Sync

Each device sends its complete auth state (device token, authoritative Client, server date, and clear generation) through `updateApplicationContext` whenever it changes. The clear generation counts clears; every local clear increments it and both devices keep the maximum they have seen. The receiver applies the incoming state as one external identity transition if `WatchSyncState.supersedes(_:from:)` says it wins:

1. Different clear generations favor the newer generation in either direction. Clearing the Watch clears the phone too. A post-clear anonymous Client carries the same newer generation and propagates the clear even if it replaces the tokenless payload before delivery. A payload with an older generation cannot restore the pre-clear identity.
2. Same token or same Client ID: the newer snapshot wins (server date, then `Client.updatedAt`). Signing in or out can rotate the token while keeping the Client ID. A newer signed-out snapshot therefore replaces the older signed-in snapshot on either device. If both timestamps tie but tokens differ, the phone's token wins.
3. Different Clients at the same generation: a tokenless state does not represent a new clear, a device without a token accepts one, and a phone awaiting the Client for its token rejects a different Watch identity until that refresh resolves. The Watch can retain its signed-in snapshot during that wait. For resolved identities, a Client with an active or pending session beats one without usable sessions, and otherwise the phone wins. Ended, expired, and other terminal sessions do not count as signed in.

A receiver replies with its own state only when that state would win on the other device, so exchanges converge without loops. Adopting a token without a Client refreshes the Client from the server. Only the phone's environment is adopted. Unversioned payloads from earlier SDKs count as generation 0. Versioned SDK 1.5 phone messages retain their token/auth ordering: an explicit phone clear advances the local clear generation, older or repeated messages cannot undo it, and a later phone sign-in can follow it. These per-app phone watermarks commit with the identity. Once a current-schema phone message is received, subsequent legacy phone messages are ignored. Older Watch-only clears remain local and are not applied to the phone. After upgrading, a phone clear recorded by SDK 1.5 starts the generation at 1. An old Watch-only clear does not advance the generation, because upgrading must not reinterpret it as a request to clear the phone. Existing new-protocol generations are always preserved. Outgoing snapshots also include the SDK 1.5 state/version fields for older paired apps. A per-app publication journal persists a version and snapshot fingerprint before sending, above the previous SDK’s committed and pending counters. The version is a persisted incrementing counter, never a timestamp, so normal publication fits the 32-bit `Int` used by arm64_32 Watch devices. Incoming legacy token/auth versions raise its floor before adoption or a reply, even when that snapshot loses. Retries reuse the version; subsequent clears and sign-ins advance it even after restart or clock rollback. Counter exhaustion reports an error rather than wrapping. A failed publication-journal write prevents sending; a failed peer-floor write prevents adopting that payload so delivery can retry. A fresh empty installation does not send a legacy clear. Public and reconfiguration clears retain the numeric legacy counters and delete the old metadata record only after preserving its highest committed or pending version. They separately save the committed, phone-attributed receive versions in the per-app journal, scoped to the app and Clerk instance. These receive versions bootstrap ordering only until the identity record contains its own phone ordering; pending and Watch-attributed counters cannot reject an incoming phone message. If either preservation fails, cleanup keeps the source metadata for a retry while still clearing credentials.

The scalar counter does not distinguish independent clears made while both devices are disconnected; those can have equal generations. Equal-generation states use the Client and device rules above. This protocol does not establish a total order between independently performed offline actions.

Server clears and observed sibling-app clears also advance the local Watch fence before publishing their state. Each app advances beyond its own previous Watch generation when it observes an unseen clear, unless the incoming generation already accounts for that clear and exceeds the local value. A sibling with a lower counter therefore cannot leave old Watch snapshots eligible to restore the login. The observed clear epoch and the chosen local generation are persisted together before updating the Watch counter, so failed writes and restarts retry the same value instead of counting the clear again. These observations use the clear-intent journal's app-specific service, so unscoped Keychain queries cannot mistake a sibling's observation for this app's. Incoming Watch transitions require a readable generation and commit that generation with their identity in the same record. It becomes a lower bound for each observing app's private counter; the record also identifies the clear already covered by that generation. Counter-write failures block identity publication and recover from the committed record on retry or restart. A rejected or failed identity write cannot advance its generation.

A Watch can clear and then refresh or sign in before its next delivery, so the receiver may see only the final snapshot with a token. An accepted generation above the receiver's local counter records a new clear and identity epoch with that snapshot, even if the token is unchanged. Siblings then reject pre-clear Watch snapshots and in-flight responses. The comparison uses the receiver's local counter: an echo or fresher snapshot at an already-known generation does not create another clear.

If the launch-time Keychain read failed, the controller recovers the persisted identity before deciding whether incoming Watch state wins. Token comparisons and response payload preparation also wait for that recovery, including when shared-session sync is disabled.

Clears and identity replacement cancel obsolete Watch client refreshes. A newly adopted token can start its own refresh immediately, and completion of an older task cannot discard tracking for the new task. Each refresh is associated with the existing client-response generation.

## Clear And Reconfigure

`clearAllKeychainItems()` signs out the in-memory Client, replaces the identity with a credential-free tombstone, records that committed clear for Watch sync, and deletes every other Clerk Keychain item except non-secret markers. When the identity is in an access group, a clear signs out every app sharing it. With Watch connectivity enabled, a clear on either paired device reaches the other; when the receiving phone shares its identity, its sibling apps also adopt that clear.

After an app disables sharing and moves its identity locally, a clear leaves the group's identity in place. Re-enabling sharing adopts the group's current identity. The last app to write a shared record is not necessarily its only user, so a local clear does not use last-writer metadata to delete the group's record.

Reconfiguration clears Clerk storage for the source and destination configurations without migrating the previous identity. An identity stored in an access group belongs to every app and extension in the group, so reconfiguration leaves it; a destination for another Clerk instance ignores it.

Destination preparation resolves storage routing without importing credentials. After local clearing succeeds, an empty destination receives a signed-out record before migration and storage handoff resume; an existing V4 destination group record is preserved. Ordinary startup migration then cannot restore the cleared login on a later launch. Changing sharing options between launches remains a separate operation that preserves the login as described below.

If reconfiguration fails, rollback reloads the complete persisted identity, including its Client and server date. It never combines a sibling's new token with the previous Client in memory, and responses prepared before reconfiguration remain fenced after rollback.

## Migration From Earlier Versions

When an app changes `sharedSessionSync` between launches while keeping the same Keychain service and access group, an explicit storage handoff preserves its identity. Disabling sharing copies the current group record locally once and leaves the shared record in place. Subsequent local launches retain their own state, including a local clear. Re-enabling sharing adopts the existing group record, including a sign-out, or seeds an empty group from the local identity. A private storage-selection marker handles repeated mode changes and interrupted handoffs; the identity and Watch ordering metadata move together. The marker is scoped to this app, Clerk instance, and configured service, and records the actual backend and its clear-intent scope. It also retains the isolated local backend’s previous clear scope while a group is selected. When a sync-option change keeps the same backend, preparation recovers any clear under its previous scope before exposing credentials or completing the scope change. Clears belonging to a separate local identity are not applied to an established group.

Legacy format migration is recorded once per app. Before creating the first group record, it reads the SDK 1.5 owner slots and selects the winning publication using the old generation, server-date, owner, and event-ID ordering. This also works for a first-upgrading app with no local identity: a sibling's published login seeds the record instead of being hidden by a new anonymous identity. A newer published sign-out takes precedence over an older signed-in local copy. No legacy slot is written during migration.

If there is no publication, migration falls back to the SDK 1.5 atomic local record, then a current-format identity in the configured app-local or previous bundle-ID service, then the earlier separate token item. Current-format imports retain the identity and Watch ordering metadata, recover pending clears first, and still run when an earlier format migration already completed but the destination backend is empty. Atomic records and publications retain their complete identity. Separate legacy items cannot prove that their cached Client belongs to their token, so only the token is migrated; the next successful server refresh supplies its Client and server date. Until then, that particular legacy migration has no cached Client, including while offline. It also understands the earlier unwrapped atomic snapshot. Apps that adopted shared-session sync in SDK 1.5 skip the separate items, which that adoption left stale. An app that disabled sharing and keeps an app-local identity does not adopt sibling publications.

For separate legacy credentials, migration checks the current configured app-local service first. When enabling sharing with a common service, it next checks the previous bundle-ID service, then the configured shared legacy items. This preserves an existing login when the service name changes during first adoption. An unreadable source defers migration. Sources from another service or backend are durably marked as retired once the destination is established, so returning to an earlier configuration cannot restore an old login. A non-secret retirement journal is written before copying; if the process exits before recording completion, the next launch checks whether the destination exists. A failed copy leaves its source recoverable while its destination can be checked. If the group entitlement is removed before retirement completion, the app conservatively fences the source and recovers into isolated signed-out local storage; temporary Keychain failures still defer recovery. Removing an access group after migrating, even with shared-session sync disabled, selects isolated local storage instead of reopening a retired V4 source. An empty local destination copies the replacement record and recovers its pending clear first; an inaccessible former group with a missing entitlement starts locally signed out. Later local logins and clears stay local. Existing group records, including clears, remain authoritative. Explicit reconfiguration still suppresses importing old credentials.

Private-state adoption uses a separate marker from SDK 1.5's identity adoption. Completing private-state adoption does not suppress legacy credentials: an exit before identity migration must leave the login recoverable on the next launch. The old identity-adoption marker is checked again during migration preparation if storage was temporarily unreadable.

Failed adoption-marker reads leave the storage layout unresolved. Reads and writes retry layout discovery instead of selecting shared storage. Migration preparation also rechecks shared-group availability, so a temporary launch failure does not suppress legacy credentials after recovery. Only a missing entitlement selects the local fallback for both identity and private data, with migration left incomplete. Shared notifications start after successful hydration, including when storage becomes available later in the same process.

The missing-entitlement fallback is recorded before its identity can be exposed. Changing the sync option or removing the unavailable group retains that isolated backend and recovers its pending clear under the previous scope. Fixing the entitlement adopts an established group record or seeds an empty group from the recovered local identity. If the app later removes that group, handoff follows its current identity instead of reopening the earlier fallback copy. When fallback is selected, Watch ordering metadata uses local storage without consulting the inaccessible group. A local clear therefore remains usable across requests and relaunches, even when Watch connectivity is disabled.

An interrupted staged publication competes with all published slots using that same ordering, instead of reverting to the older accepted identity. Invalid publication ownership, conflicting copies, and unsupported records stop migration and preserve its source. A failed slot enumeration is not treated as an empty group. Locked storage is retried before hydration and request preparation, so the app cannot bootstrap an empty identity over temporarily unavailable credentials. A missing shared-group entitlement still permits migration to the app-local fallback.

When another app already wrote the new record, it is authoritative, including a signed-out snapshot or clear tombstone. Old credentials must not overwrite it. A migration races safely using conditional creation. The slot import preserves the old group's known identity before the first record exists; it does not guess whether an already-existing anonymous record was never signed in or was deliberately signed out. A private legacy login that was never published cannot automatically replace an established group identity. A shared-session clear interrupted in SDK 1.5 is honored by writing a clear tombstone if no group record exists. The earlier clear journal is retained until all credential cleanup succeeds.

The migration deletes app-attributed atomic records and this app's SDK 1.5 owner slot. It preserves separate legacy items and retired current-format sources whose private ownership cannot be established: an unscoped Keychain deletion could also remove a sibling's credentials. Retirement and format-migration markers prevent this app from importing those retained credentials again. The migration is marked done only after the required retirement and cleanup succeed, and not while the access group is unreachable, so incomplete work retries on the next launch.

Apps on SDK 1.5 and later versions do not see each other's shared sessions; update every app that shares an access group together.

## Private State

The shared record holds the same token/Client information previously published in slots. App Attest identifiers, pending magic-link state and biometric credential metadata continue through app-local stores. When enabling sharing with a common service, adoption preserves unexpired magic-link flows and App Attest identifiers from the trusted previous bundle-ID service, without overwriting existing destination values. Adoption does not import another app's App Attest identifier or PKCE state from ambiguous shared legacy storage. Keychain access groups enforce permissions; owner-slot naming was an SDK convention, not a per-app Keychain write permission. The current app-local storage setup still relies on the host's default Keychain access-group configuration; service naming does not change Keychain access permissions.
